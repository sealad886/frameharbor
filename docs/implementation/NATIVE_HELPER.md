# Native filesystem helper evidence

Updated 9 November 2026. The selected synthetic M3 adapter is under qualification. The native helper accepts image length, image-relative filesystem start, the explicit `fat32`/`exfat` profile, and one directory inode/entry cursor with entry/run budgets. It accepts no source filename or image descriptor. All source reads are requested as byte ranges over pipes and served through the Rust acquisition/case-budget authority. Requested cache bytes and delivered acquired bytes are reported separately. When speculative TSK prefetch crosses an acquisition hole, only its positive contiguous acquired prefix is delivered. Missing prefixes and malformed replies terminate the child; unavailable bytes are never filled or presented as read successfully.

The sole native invocation is `helper image_size fs_start profile batch inode_or_root next_entry entry_limit run_budget`. It opens that directory directly and processes its entry indices; there is no recursive root-walk or skip-N path. A run-budget boundary stops before emitting the next file and returns its unchanged entry index for the next batch. `filesystem::inspect` is a bounded small-namespace convenience over this same batch engine; production uses the durable paged Ledger queue. Cleanup observers receive one actual result per child, including failures.

The declared namespace is `allocated-reachable-native-names-v1`. Pinned TSK synthetic virtual files and its virtual orphan directory are excluded by type and counted explicitly. A real directory with the same name is included. Deleted or unreadable real directories remain deferred, preventing global qualification. Dot entries and exact `.DS_Store` names are ignored; files remain untouched. This scope does not claim an orphan search or whole-image namespace completeness.

## Actual resource envelope

The helper validates matching 4.14.0 headers/runtime and links the explicitly selected installed `/usr/local/lib/libtsk.23.dylib`. The co-installed `.22` library is a mismatching 4.15.0-develop build; filename ordering cannot choose a safe ABI. See [the ABI/cache experiment](TSK_PROBE.md).

Each C child enforces 30 CPU seconds, no core/file output, at most 8,192 read callbacks of at most 1 MiB, 1,024 entries/files, 1,024 runs per file, a maximum 1,024 aggregate runs per batch, and 65,536 allocation-block checks. Rust supervision additionally bounds wall time, output, source bytes, protocol records and managed buffers, and kills/waits the owned helper on cancellation, timeout or malformed responses. Initial admission includes 2 MiB of archive/checkpoint overlap while the child remains resident. Already reserved parser work uses fresh source/control guards; reads, archive writes and final elapsed settlement retain durable admissions. These are resource/process isolation properties, not a certified OS security sandbox.

The [published TSK 4.14 directory API](https://raw.githubusercontent.com/sleuthkit/sleuthkit/sleuthkit-4.14.0/tsk/fs/fs_dir.c) materializes an entire individual directory before indexed entry access. Batch output and Rust memory are bounded, but a very large flat directory may exceed native memory/time limits and remain explicitly unenumerated. Reopening a cursor also rereads that directory; it does not reprocess earlier entry metadata. No arbitrary namespace throughput claim follows from the synthetic multi-directory tests.

An initial absolute `RLIMIT_DATA=64 MiB` failed with `EINVAL` on this Mac before `HELLO`. Separate synthetic child probes showed 64 MiB, 256 MiB and 4 GiB fail, whereas 1 TiB succeeds. The current Apple [resource implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_resource.c) and [VM limit implementation](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/vm/vm_map.c) explain the observed behavior: DATA/AS limits are validated against the already mapped address space. This is consistent with this host's approximately 500 GiB preloaded virtual map, which is not resident memory.

The corrected Darwin helper measures its initial Mach virtual size and applies DATA/AS ceilings at that value **plus 64 MiB**. This caps additional virtual mappings; it does not claim an absolute 64 MiB RSS limit or control resident pages within pre-existing mappings. Linux uses its separate DATA/RSS policy. The helper reports measured maximum RSS on successful runs. Rust admission conservatively reserves a 256 MiB child envelope plus its overlapping IPC/parser buffers; final real hardware/RSS/system-pressure qualification remains M7 work. Unsupported resource setup fails before source data is requested rather than silently dropping limits.

## Source and ownership evidence

The helper preserves file/name/attribute/run flags and filesystem block units. Rust converts logical and physical block coordinates with checked arithmetic and the explicit filesystem start. TSK blocks are not assumed to be allocation clusters. Deleted metadata, RECOVERY/FILLER/SPARSE/encrypted runs, incomplete initialization and unsupported skips cannot become exact mappings merely because native parsing succeeded. Allocation checks use TSK's address-only block walk, including current FAT/bitmap evidence. Negative checks and checks not performed because of the cap are distinguished; unchecked run ordinals remain explicit and cannot establish allocated ownership. Resumable allocation qualification beyond this cap remains separate work.

Completed file callbacks remain provisional. Source observations must reach a sealed durable frontier before the Ledger adopts a batch cursor. Global geometry qualification waits for the selected directory domain to finish without deferred real metadata. Independent batch tests exercise 1,100 file entries across directories and pages, same-Ledger resume, aggregate-run early stopping, metadata holes, malformed cursors, and child cleanup. They are development regressions, not untouched holdouts or real-image yield evidence.

Equal geometry and crosslinks retain separate logical owners. Source acquisition holes remain unavailable even when stale fixture bytes look like MP4; helper read failures do not substitute those bytes. A qualified extent view is still no proof of original pre-damage content, encoded-media validity or playback.

## OS sandbox experiment, not enabled

The experimental [source-read allowlist profile](experiments/tsk-read-allowlist.sb) is retained as failed qualification evidence and is **not used by the Rust adapter**. Applying a nested macOS seatbelt profile in the normal Codex sandbox returned `Operation not permitted`. An approved external synthetic in-memory probe with write/network denial succeeded; the stricter read allowlist aborted with status 134 before output despite allowing the canonical installed dependency paths. No source image was opened by these probes. Neither attempt certifies filesystem parser confinement against exploitation.

Normal helpers currently use the explicit bounded process/resource envelope above. A compromised native parser is not proven unable to open unrelated files or contact host services. Real recovery remains disabled/unauthorized; OS confinement and the real host/resource envelope must be qualified before enabling that runtime profile. No permission to run real images follows from successful synthetic extent tests.
